# Итоговая архитектура

## 1. Суть решения

Система состоит из двух контуров.

- **Узел подстанции (edge)** стоит на подстанции. Он читает RTSP с камер, находит людей нейросетью YOLO и отправляет детекции в центр. Для детекции узел передаёт собственное логическое значение `is_alert`.
- **Центр (главный офис)** принимает события и создаёт тревогу при пересечении запрещённой зоны без подходящей заявки.

Главное решение: **заявки на узел не передаются**. Для проектируемого сопоставления с заявкой используется время `detected_at`. Так устаревшая копия заявок не может подавить настоящую тревогу.

## 2. Компоненты узла

Развёртываются в docker-compose на подстанции.

| Компонент | Задача |
|---|---|
| Supervisor | Берёт список камер из локальной БД и запускает по одному воркеру на камеру, раз в 30-60 с сверяет список |
| Воркеры камер | Читают RTSP, берут 2-5 кадров/с, переподключаются с нарастающей паузой, ловят зависший поток (watchdog), кладут кадры в Redis Stream с ограничением длины |
| Инференс | Один экземпляр YOLO (класс `person`), определяет зону ROI, объединяет повторные детекции одного человека (трекинг/пауза) |
| Локальная БД | SQLite или лёгкий PostgreSQL |
| Локальный MinIO | Снимки, хранение ограничено 7-30 днями |
| Redis | Очередь кадров между воркерами и инференсом |
| Outbox-воркер | Отправляет события в центр, повторяет при ошибках |
| Heartbeat и синхронизация | Раз в 10-15 с heartbeat, раз в несколько минут обновление камер и зон |
| MediaMTX | Раздача видео диспетчеру (см. открытые вопросы) |

**Локальная БД узла (5 таблиц):** `cached_cameras`, `cached_roi_zones`, `detections` (PK `event_uuid`), `outbox`, `sync_state`. Таблиц `cached_requests` и `alerts` на узле нет.

## 3. Компоненты центра

| Компонент | Задача |
|---|---|
| Backend (Flask) | REST API и WebSocket для веб-интерфейса диспетчера |
| Обмен с узлами | Топики `camera.status`, `camera.detections`, `node.heartbeat`. Consumer подтверждает offset после фиксации результата в PostgreSQL |
| Сервис сопоставления | Для `is_alert=true` центр проверяет активную неудалённую заявку на момент обнаружения |
| Повторная доставка | Уникальность UUID события и `alerts.detection_id` защищает от повторного создания тревоги |
| Контроль узлов | Фоновая задача: нет heartbeat 2-3 интервала подряд → `offline` и запись в журнал |
| Сервис отчётов | Агрегации, CSV/Excel |
| Аудит | Middleware для действий пользователей, запись системных событий узлов |
| PostgreSQL | Основная БД |
| MinIO | Постоянное хранилище снимков |
| Redis | Тикеты для WebSocket, рассылка тревог между процессами |
| nginx | TLS, reverse proxy, rate limit, проксирование WebSocket |
| Frontend | Адаптивное веб-приложение: панель диспетчера, админка, журнал, аналитика |

Центр хранит детекцию с уникальным `event_uuid` узла. Поле `detections.matched_request_id` предназначено для результата сопоставления с заявкой. Новая заявка получает статус `pending`, подтверждённая — `active`. У детекции может быть не более одной тревоги. Центр присваивает ей собственный `alerts.id`. Все десять таблиц и их связи приведены в [схеме центральной БД](БД%20центра.md).

## 4. Взаимодействие

Узел назначает камере номер в пределах подстанции. В обоих сообщениях `Sender` содержит ID подстанции в центре. Имя поля локального номера камеры зависит от типа события. Ключ записи Kafka передаётся отдельно как `Sender:номер`, например `10:1`. Эта же пара образует первичный ключ `cameras` в PostgreSQL.

| Направление | Протокол | Что передаётся |
|---|---|---|
| Узел → центр | Kafka, статус камеры | `id`, `Camera_id`, `Time`, `Viable`, `Sender`. Поля передаются с указанным регистром. `Viable` — логическое значение |
| Узел → центр | Kafka, детекция | `id`, `camera_id`, `zone_id`, `detected_time`, `person_count`, `confidence`, `is_alert`, `file`, `Sender` |
| Центр → браузер | WebSocket (`/ws/alerts`) | Новые тревоги в реальном времени |
| Браузер → центр | REST | Всё остальное: заявки, тревоги, отчёты, справочники |

Принципы доставки:
- узел всегда клиент, входящих подключений на подстанцию нет;
- событие пишется в `detections` и `outbox` в одной транзакции;
- центр отсекает дубли по `event_uuid` (`ON CONFLICT DO NOTHING`);
- `file` содержит путь к снимку. Способ, которым центр получает доступ к файлу, требует отдельного согласования;
- `id` содержит UUID события и сохраняется при повторной отправке;
- `is_alert` во входном сообщении означает пересечение запрещённой зоны. Центр сохраняет результат решения в связи с заявкой или в `alerts`.
- предлагаемый heartbeat передаётся с ключом `7` и телом `{"node_id":7,"Time":"2026-11-25T12:00:00+03:00"}`. Формат синхронизации конфигурации камер и зон остаётся открытым.
- потерю и восстановление связи с камерой узел публикует в Kafka с `Viable: false` и `Viable: true` соответственно.

## 5. Безопасность

| Что | Решение |
|---|---|
| Пользователи | Собственная аутентификация на JWT, хеш пароля, роли `dispatcher`, `admin`, `auditor` |
| Узлы | Учётные данные и права публикации в Kafka предстоит настроить. `Sender` обозначает подстанцию в теле сообщения |
| Канал | TLS на nginx (HTTPS и WSS), система в защищённом контуре |
| WebSocket | Одноразовый тикет (получается по REST, живёт 10-30 с, хранится в Redis) или токен первым сообщением. Проверка роли при подключении, закрытие соединения по истечении токена, `limit_conn` в nginx |
| Журнал | Время, IP, пользователь, операция |
| Ограничение частоты | nginx `limit_req` и защита в приложении |
| Время | NTP/chrony на узлах |

Keycloak в проект не входит и описывается как направление развития (SSO, LDAP/AD, 2FA).

## 6. Как считаются показатели ТЗ

| Показатель | Формула |
|---|---|
| Время от детекции до создания тревоги в центре | `alerts.created_at − detections.detected_at` (при синхронизации часов узла и центра по NTP) |
| Задержка доставки | `detections.received_at − detections.detected_at` |
| Ложные срабатывания | Доля `alerts.status = 'false_positive'` |
| Корректность классификации | `matched_request_id` и факт тревоги против эталона сценария |
| Полнота журналирования | Записи в `detections`, `alerts`, `audit_log` |

## 7. Открытые вопросы

1. **Живое видео диспетчеру.** Если видео остаётся на подстанции, нужен доступ к MediaMTX узла по VPN и по запросу. Мы это не решили: либо MediaMTX на узле и доступ через VPN, либо отдельный упрощённый путь для курсовой (демо на одном сервере).
2. **Масштаб демонстрации.** Для курсовой достаточно двух compose-стеков: один «узел», один «центр». Несколько узлов, отказоустойчивость и Keycloak описываются как развитие.
3. **Правки ТЗ.** Разделы 4.1 (состав: узел), 4.3 (аутентификация узла, канал узел-центр), 2.2 (устойчивость к потере связи), 7 (подготовка узла).
