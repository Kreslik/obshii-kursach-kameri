# Архивное предложение о регистрации камер по UUID

Этот вариант описывает прежний обмен по HTTP. Для целевого обмена через Kafka см. [описание взаимодействия](Уточнения%20для%20создание%20структуры%20проекта.md).

В действующей схеме первичный ключ камеры составной — `(substation_id, camera_id)`. В событиях Kafka эти значения поступают как `Sender` и `Camera_id` или `camera_id` в зависимости от топика. Таблицы и связи приведены в [БД центра](БД%20центра.md).

Ниже описан вариант развития, при котором узел сам регистрирует камеры, назначает им UUID и хранит пароль RTSP на подстанции. Примеры API и SQL в этом документе относятся к предлагаемому варианту.

## 1. Идентификатор: `camera_uuid`

Это тот же приём, что и с `event_uuid`. Числовые `id` у разных узлов совпадут (у всех будет камера №1), поэтому сквозным идентификатором должен быть UUID, созданный на узле при добавлении камеры.

| Где | Ключ |
|---|---|
| Узел | `camera_uuid` как PK (числового id не нужно) |
| Центр | `id` как внутренний числовой ключ + `camera_uuid UNIQUE NOT NULL` |

Узел в детекциях передаёт `camera_uuid`, а центр по нему находит свой `camera_id`. Остальные таблицы центра (`roi_zones`, `detections`) по-прежнему ссылаются на числовой `id`.

## 2. Регистрация камеры в центре

Камера создаётся в локальной БД со статусом `pending`, затем узел отправляет её в центр:

```
POST /api/v1/node/cameras   {camera_uuid, name, rtsp_url (без пароля), ...}
```

Центр делает идемпотентный upsert по `camera_uuid`:

```sql
INSERT INTO cameras (camera_uuid, substation_id, name, rtsp_url)
VALUES (:uuid, :substation, :name, :url)
ON CONFLICT (camera_uuid) DO UPDATE
   SET name = EXCLUDED.name, rtsp_url = EXCLUDED.rtsp_url;
```

Повтор запроса безопасен. После ответа `200` узел ставит камере `synced`. Ограничения уникальности из прошлого ответа остаются в центре: `UNIQUE (substation_id, name)` и `UNIQUE (substation_id, rtsp_url)`. Подстанцию центр берёт из аутентификации узла (`edge_nodes.substation_id`), а не из тела запроса, чтобы узел не мог зарегистрировать камеру на чужой подстанции.

## 3. Порядок: сначала камера, потом детекции

Если детекция придёт раньше камеры, центр не найдёт `camera_uuid`. Решения:
- узел не отправляет детекции камеры, пока она не `synced` (самое простое);
- центр отвечает `409 unknown camera`, а узел оставляет событие неотправленным и повторяет позже.

Лучше сочетать оба варианта.

## 4. Где возможны конфликты и как их разрешать

| Ситуация | Как решить |
|---|---|
| Один и тот же адрес пришёл с разными `camera_uuid` | Центр отвечает `409`. Узел помечает камеру `conflict` и сообщает об ошибке в heartbeat. Администратор решает вручную |
| Узел переустановили, локальная БД потеряна, камеры созданы заново | То же самое: адрес уже есть. Центр может вернуть существующий `camera_uuid`, а узел его принять (привязка по адресу). Это удобнее, чем разбор вручную |
| Название занято | Тоже `409`, переименовать камеру на узле |
| Камеру удалили на узле | Не удалять физически: `is_active = false`, статус синхронизируется. История детекций остаётся |
| Два оператора правят одну камеру | Один узел, один локальный интерфейс, поэтому конфликта нет |

## 5. Правило: у каждого поля один владелец

Чтобы не появлялась двусторонняя синхронизация и «кто последний записал, тот и прав», разделите поля:

| Поле | Владелец | Направление |
|---|---|---|
| `camera_uuid`, `rtsp_url`, учётные данные, техническое состояние | Узел | Узел → центр |
| `status`, `last_frame_at` | Узел | через heartbeat |
| `name`, `is_active` | Решите сами: узел или центр | см. ниже |
| Зоны интереса (`roi_zones`) | Центр (админ рисует по снимку в интерфейсе) или узел | см. ниже |

Здесь ТЗ подсказывает ограничение: в 4.2.2 управление камерами, зонами и справочниками отнесено к администратору в веб-интерфейсе центра. Если камеры полностью переедут на узел, этот пункт нужно менять. Компромисс, который я бы взял:
- **узел регистрирует камеру** (технические данные, адрес, пароль);
- **администратор в центре её «оформляет»**: название, включение или отключение, рисует зоны ROI по снимку.

Для передачи зон и флага `is_active` можно использовать предусмотренный проектом маршрут `GET /api/v1/node/cameras`.

## 6. Пароль от камеры не должен попадать в центр

Одно из главных преимуществ вашей идеи. RTSP-адрес с логином и паролем остаётся только на узле (в локальном хранилище, лучше в шифрованном виде или в секретах Docker). В центр уходит адрес без учётных данных, и этого достаточно для идентификации и уникальности (нормализация из прошлого ответа). Для объекта КИИ это сильный аргумент в пользу вашего решения.

## 7. Изменения в БД

**Центр, `cameras`:**
```sql
ALTER TABLE cameras
  ADD COLUMN camera_uuid uuid NOT NULL UNIQUE;
```
`id` остаётся внутренним ключом, `rtsp_url` хранится без пароля.

**Узел:** таблица камер становится не кэшем, а собственным справочником, поэтому имя `cached_cameras` лучше заменить на `cameras`:

```sql
CREATE TABLE cameras (
    camera_uuid   TEXT PRIMARY KEY,
    name          TEXT NOT NULL,
    rtsp_url      TEXT NOT NULL,        -- с учётными данными, только локально
    is_active     INTEGER NOT NULL DEFAULT 1,
    status        TEXT,
    last_frame_at TEXT,
    sync_status   TEXT NOT NULL DEFAULT 'pending',   -- pending / synced / conflict
    sync_error    TEXT,
    UNIQUE (rtsp_url),
    UNIQUE (name)
);
```

В `detections` на узле поле `camera_id` заменяется на `camera_uuid` (внешний ключ на `cameras`). Таблица зон тоже получает `roi_uuid`, если зоны могут появляться на узле.

В центральной `detections` ничего менять не нужно: центр переводит `camera_uuid` в `camera_id` при приёме.

## 8. Итог

1. Идентификатор камеры создаётся один раз на узле и не меняется (`camera_uuid`).
2. Регистрация идёт идемпотентным upsert, повтор безопасен.
3. Дубли отсекает уникальность `(substation_id, rtsp_url)` и `(substation_id, name)` в центре.
4. Детекции отправляются только для синхронизированных камер.
5. У каждого поля один владелец, поэтому двусторонних конфликтов нет.
6. Пароль камеры остаётся на узле.
