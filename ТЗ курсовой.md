- Назначение и цели создания системы
2.1 Назначение системы:
Система предназначена для автоматизации видеонаблюдения за территорией подстанций, обнаружения несанкционированного проникновения нейросетевой моделью, сопоставления фактов присутствия с заявками и оповещения диспетчера-безопасника.
2.2 Цели создания системы:
Цель — замена непрерывного ручного отсмотра видеопотоков диспетчером на автоматическое обнаружение событий с реакцией человека только на сформированные тревоги.
Цель достигнута при выполнении измеримых показателей, проверяемых на тестовом прогоне:
 
- Полнота обнаружения — доля сценариев с человеком, при которых сформирована детекция, не менее 95%.
 
- Корректность классификации — доля сценариев, где решение системы совпало с эталонным (тревога без заявки / отсутствие тревоги при активной заявке), не менее 95%.
 
- Время реакции — от появления человека в кадре до тревоги не более 3 секунд.
 
- Доля ложных срабатываний — не более 15% от общего числа тревог.
 
- Снижение ручной нагрузки — работа системы без участия оператора на этапе обнаружения.
 
- Полнота журналирования — 100% событий (детекция, тревога, действие диспетчера, изменение заявки) зафиксированы в журнале.
2.3 Методика оценки достижения целей:
Оценка проводится по результатам тестового прогона на наборе сценариев (легальное проникновение, нелегальное, группа людей, пустая территория, зона интереса) с заранее известным эталонным решением.
Источники данных: журнал событий с временными отметками, карточки тревог со статусами, сопоставление решений системы с эталоном.
Результат оформляется таблицей «факт — норматив» по каждому показателю.
 
- Описание объекта автоматизации
Автоматизации подлежит сквозной процесс видеомониторинга территории подстанций: от получения видеопотока с камер до обработки специалистами и изменения статусов тревог.
Особенности объекта автоматизации:
• на территории подстанции в штатном режиме люди отсутствуют;
• легальное присутствие возможно только в рамках заранее оформленной заявки (ремонт, обход, проверка), которая известна системе;
• все проникновения вне заявок считаются инцидентом и требуют реакции диспетчера-безопасника;
• подстанция — стратегический объект критической информационной инфраструктуры, доступ к системе ограничен, каналы связи должны быть защищены.
 
- Требования к системе
4.1 Требования к архитектуре системы
• трёхуровневая архитектура (клиент — сервер приложений — база данных);
• клиентская часть реализована в виде адаптивного веб-приложения;
• серверная часть — на Python , модуль инференса на базе предобученной нейросетевой модели YOLO, брокер сообщений Redis;
• система управления базами данных — PostgreSQL; хранилище видео и снимков — MinIO/S3;
• передача видеопотока — RTSP → сервер → HLS/WebRTC для клиента;
• простота обслуживания и эксплуатации (минимальные требования к квалификации и дополнительному обучению эксплуатирующего персонала);
• экономичность (экономическая эффективность в процессе функционирования);
• модифицируемость (возможность перенастройки под другие объекты);
• функциональная расширяемость (возможность ввода дополнительных функций, не предусмотренных в техническом задании).
4.2 Требования к функциям, выполняемым системой
4.2.1 **Со стороны диспетчера-безопасника:**
• предоставить интерфейс авторизации с разграничением доступа по ролям (диспетчер, администратор);
• обеспечить просмотр онлайн-видеопотоков с камер подстанций в режиме реального времени;
• предоставить ленту тревог с пагинацией, фильтрацией по подстанции, камере, времени, статусу и поиском;
• обеспечить карточку тревоги: снимок кадра, время, камера, подстанция, кнопки «Подтвердить», «Ложное срабатывание», «Связать с заявкой»;
• предоставить интерфейс просмотра и управления заявками (создание, подтверждение, закрытие);
• обеспечить просмотр отчётов и выгрузку в CSV/Excel.
4.2.2 **Со стороны администратора (технических служб):**
• управление пользователями и ролями: создание, редактирование, блокировка учётных записей;
• управление справочниками: подстанции, камеры, типы заявок, зоны интереса (ROI);
• администрирование заявок: авторизованный доступ к списку заявок с пагинацией, фильтрацией по статусам, подстанциям, датам, а также поиском; изменение статуса («Активна», «Закрыта», «Отклонена»), редактирование данных заявки, служебные комментарии и удаление заявок;
• автоматическая фиксация всех действий администратора по заявке и тревоге в журнале действий;
• отчёты в виде графиков и диаграмм (распределение тревог по подстанциям, динамика поступления во времени, доля ложных срабатываний, метрика точности нейросетевой модели за текущий сеанс), выгрузка отчётов в CSV/Excel.
4.3 Требования к информационной безопасности
• аутентификация по JWT, хеширование паролей;
• разграничение доступа по ролям: «диспетчер», «администратор», «аудитор»;
• шифрование канала передачи данных ;
• изоляция системы от публичной сети, размещение в защищённом контуре;
• журналирование всех действий пользователей (время, IP-адрес, операция);
• ограничение частоты запросов .

• формирование тревоги при отсутствии активной заявки;
• отсутствие тревоги при наличии активной заявки на данной подстанции;
• отображение тревоги в панели диспетчера не позднее 3 секунд с момента обнаружения;
• корректная работа фильтров, поиска и отчётов;
• разграничение доступа по ролям;
• корректная работа выгрузки отчётов в CSV/Excel.
