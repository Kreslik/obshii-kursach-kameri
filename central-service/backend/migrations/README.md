# Миграции центральной БД

Действующие таблицы, ключи и связи PostgreSQL описаны в [схеме центральной БД](../../../БД%20центра.md).

Начальные таблицы PostgreSQL создаёт ревизия [0001_central_schema](versions/0001_central_schema.py).

Ревизия [0002_alert_detection_unique](versions/0002_alert_detection_unique.py) добавляет ограничение `UNIQUE` для `alerts.detection_id`. У одной детекции может быть ноль или одна тревога. Первичным ключом тревоги служит `alerts.id`.

Ревизия [0003_drop_alert_received_at](versions/0003_drop_alert_received_at.py) удаляет `alerts.received_at`. Время приёма детекции хранится в `detections.received_at`, время создания тревоги центром — в `alerts.created_at`. При откате Alembic создаёт столбец `alerts.received_at` заново и заполняет его значением `alerts.created_at` каждой тревоги. Если до миграции эти значения различались, для восстановления прежнего `received_at` понадобится резервная копия.

Ревизия [0004_camera_station_key](versions/0004_camera_station_key.py) добавляет номер камеры, назначаемый узлом, и уникальность пары `(substation_id, local_camera_id)`. Для существующих камер миграция копирует `id` в `local_camera_id`, чтобы прежние сообщения находили ту же камеру. При откате столбец локального номера удаляется.

Ревизия [0005_kafka_camera_events](versions/0005_kafka_camera_events.py) переносит ссылки зон и детекций по старому `cameras.id`. Новым первичным ключом служит `(substation_id, camera_id)`, где номер камеры взят из `local_camera_id`. PostgreSQL выполняет перенос в одной транзакции с блокировкой записи. Прежние значения `detections.frame_key` сохраняются в `file`. У исторических детекций `is_alert` равен NULL, а `cameras.status_at` заполняет первое событие статуса.

При откате на 0004 Alembic создаёт новые сквозные номера камер и восстанавливает ссылки зон и детекций. Для восстановления именно прежних сквозных номеров нужна копия БД до миграции. Значения новых полей `is_alert` и `status_at` при откате теряются.

Модель включает десять таблиц: `users`, `substations`, `edge_nodes`, `cameras`, `roi_zones`, `request_types`, `access_requests`, `detections`, `alerts`, `audit_log`. Текущая ревизия хранится в служебной таблице `alembic_version`.

- Идентификатор входящей детекции `detections.event_uuid` уникален. Это защищает от повторной доставки при восстановлении связи с узлом.
- Тревогу создаёт центр. Индекс по `alerts.substation_id`, `status` и `created_at` поддерживает поиск свежих тревог по подстанции.
- На подстанции может быть несколько узлов. Составной внешний ключ разрешает назначить камере только узел её подстанции. Поле `cameras.node_id` можно оставить пустым до назначения.
- Для новой заявки выбран начальный статус `pending`. После подтверждения заявка переходит в `active`. Период действия хранится в `timestamptz`; конец должен быть позже начала. При изменении заявки PostgreSQL обновляет `updated_at`.
- В `audit_log` уникальность `event_uuid` защищает журнал от повторной записи события с тем же идентификатором. Триггер блокирует изменение, удаление и очистку журнала.

## Ревизия 0006

[0006_detection_decision](versions/0006_detection_decision.py) удаляет столбец `detections.is_alert`. Флаг остаётся в контракте Kafka. Связь с заявкой и созданная тревога описывают результат решения. Исторические записи журнала остаются доступными для дедупликации. Уникальность `alerts.detection_id` сохраняется. Существующие детекции при миграции сохраняют свои исходные связи.

При откате на 0005 столбец восстанавливается как nullable boolean со значением NULL. Исходные значения столбца можно восстановить из резервной копии перед 0006.

Перед запуском `docker compose up --build` на существующем центре остановите consumer, выполните `pg_dump -Fc` основной БД и скопируйте архив из контейнера. Восстановите его командой `pg_restore --single-transaction --exit-on-error` **в отдельную пустую БД**. Сверьте ревизию и данные таблиц и проверьте `alembic upgrade head` и `alembic check` на восстановленной БД. Затем запускайте обновление основной базы. Результат проверки текущей установки указан в [README](../../README.md#проверка-на-отдельной-бд-и-брокере).

## Применение и демонстрационные данные

При запуске Compose одноразовый сервис `migrate` выполняет `alembic upgrade head` до запуска Flask и consumer. Следующие команды выполняются при работающем backend из каталога `central-service`.

```powershell
docker compose exec backend alembic upgrade head
docker compose exec backend alembic current
docker compose exec backend alembic check
docker compose exec backend flask --app app seed-demo
```

`current` показывает ревизию, `check` сравнивает схему БД с метаданными ORM. Демоданные загружает отдельная команда в одной транзакции. Повторный запуск для уже существующего кода `DEMO-PS-01` сохраняет записи и выводит ID камер подстанции.

| Объект | Значение |
|---|---|
| Подстанция | `DEMO-PS-01` («Учебная подстанция») |
| Узел и камера | `demo-edge-01`, `demo-camera-01`; адрес RTSP служит примером |
| Заявка | «Демонстрационный обход», статус `active`, один человек |
| Период | 23 ноября 2026 года с 09:00 до 12:00 UTC (с 12:00 до 15:00 по Москве) |
| Автор | Служебная заблокированная учётная запись `demo_seed_author` |

При первом создании команда генерирует ключ узла и показывает его один раз. Если передать переменную окружения `DEMO_NODE_API_KEY` в процесс команды, будет использовано её значение. В таблице узлов хранится хеш.

Подставьте оба числа из пары, которую вывел `seed-demo`: сначала ID подстанции, затем номер камеры.

```powershell
docker compose exec backend flask --app app show-camera 1 1
```

Проверки старой схемы с данными, обновления, отката и повторной загрузки демоданных выполняются в отдельных схемах тестовой PostgreSQL. [Команды запуска и результаты](../../README.md#проверка-на-отдельной-бд-и-брокере).
